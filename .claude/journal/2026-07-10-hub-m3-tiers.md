# 2026-07-10 — Hub M3: tiers + entitlements + platform webhooks + gating

**The move.** Chad's matrix (basic = channels only; pro = everything) made real end to end:
`TIER_FEATURES` in contracts, an entitlement JWT the desktop verifies offline against a pinned
key, the platform webhook surface (HMAC + replay dedup), a hosted set-password page, and tier
gating on both the daemon routes and the UI. Full gate 2101/4-skip; reviewer found ONE must-fix
(token-type confusion) + should-fixes, all applied.

## Learnings worth keeping

- **Two JWTs from one key = token-type confusion waiting to happen.** The entitlement token
  (7-day) satisfied the access verifier (same key + issuer, all claims present) — a PoC-confirmed
  privilege path the reviewer caught. Fix: a `token_use` claim each verifier REQUIRES, plus
  explicit `algorithms: ['EdDSA']`, constants shared in contracts. Any time you sign two token
  kinds with one key, give them distinct `token_use`/`aud` and check it on BOTH sides.
- **Webhook idempotency needs a dedup LOG, not just idempotent handlers.** Convergent handlers
  stop duplicates from corrupting state, but a replayed upgrade-after-downgrade inside the HMAC
  window still flips the tier. A `platform_events` table (event id PK, ON CONFLICT DO NOTHING)
  makes application exactly-once — the id was already in the contract, only unused.
- **Sign HMAC over the RAW body + raw timestamp string, verify before parsing.** Re-serialized
  JSON won't match the platform's bytes. Cap the pre-auth body (bodyLimit) so a large POST can't
  be buffered before the signature check.
- **"No entitlement" must read the same on both seams.** The daemon gate is permissive without a
  verified entitlement; when the desktop couldn't verify the token (key mismatch) it stamped
  `basic`/`[]` into the status, so the UI locked everything while the API allowed it. Carrying
  tier/features as NULLABLE (null = unproven) makes UI and API agree — null → don't gate.
- **Incremental migrations, live-proven.** The hub DB is a real docker volume now, so 0001/0002
  are incremental (never edit 0000). `node --watch` reloading the running hub applied them to the
  existing volume without a crash — the migration-on-populated-DB path PGlite tests can't cover.
- **Cross-leaf tests belong on the app side.** A hub-account test that imported `@vynel/accounts`
  would break the no-sibling-leaf rule; hand-signing tokens inline with jose keeps the leaf pure
  (the cross-leaf pairing already lives in apps/cloud-api).
